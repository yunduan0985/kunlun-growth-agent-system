# 🤖 如何把你的业务流程做成 AI Agent 员工

> **作者**：鹿书野 | B站好物深海圈教练 | 生财有术资深传术师
> **背景**：月均带货 GMV 500w+，搭建内容工厂，与@蛋哥成立工作室跑通 1-10

---

## 💡 核心方法论：8步构建生产级 Agent

### 第一步：从最小闭环开始，而不是追求完美系统
> 不要上来就建复杂系统，先跑通「输入→处理→输出」的最小单元

### 第二步：用对话跑通业务逻辑
- 先和 AI 在对话框里把任务跑通
- **不要把聊天记忆当作系统记忆**——对话上下文会消失

### 第三步：把共识沉淀到项目文件（4类必做）

| 文件类型 | 职责 | 示例 |
|---|---|---|
| **AGENTS.md** | 全项目不可违反的原则 | 安全规则、输出格式 |
| **Skill.md** | 某类任务的完整操作顺序 | 视频字幕处理 SOP |
| **脚本** | 机械执行的数据获取/文件检查 | Cookie 检查、文件验证 |
| **验证器** | 兜底质量把关 | 输出结构完整性验证 |

> [!IMPORTANT] 铁律：脚本不能代替 AI 判断！
> 需要语义判断的工作让 AI 做，脚本只负责机械执行。
> 不能把某个句子、行号、价格写死在脚本里！

### 第四步：用飞书建立任务控制台

**核心设计**：
```
飞书多维表格（任务看板）← 业务人员下命令
        ↓
     Agent 扫描任务表（定时触发）
        ↓
     执行任务 → 归档结果 → 回写状态
```

**好处**：
- 业务人员不必进代码目录
- 不必每次重写长提示词
- 任务具备排队、查看、失败反馈和复盘能力
- 可以多个 Agent 串联（A 的输出是 B 的输入）

### 第五步：安装飞书 CLI（解锁飞书全量能力）

```bash
# 三步安装飞书 CLI
npm install -g @larksuite/cli
npx skills add https://github.com/larksuite/cli -y -g
lark-cli config init --new
```

安装后 Codex/Agent 可以**直接在飞书里干活**！

### 第六步：固化阶段 → 沉淀 AGENTS.md + Skill.md

完成最小闭环后，把业务共识沉淀到项目文件，而不是让约定停留在聊天记录里。

### 第七步：回归测试（必做！）

> 每次项目文件升级后，**必须在当前对话再执行一次任务**
> 防止改了 A，意外弄坏了 B

### 第八步：新开对话重新执行（去上下文回归测试，必做！）

> 关闭原来的长上下文对话，**在新对话里让 Agent 重新读项目文件执行任务**
> 
> 目的：验证能力是否已从「对话中的能力」变成「项目能力」
> 这是判断一个演示是否真正具备生产潜力的关键标准！

## 🏭 内容工厂架构（鹿书野实战模型）

```
文案创作：VS Code + Claude Code (CC) 插件（4.6模型）
   ↓
Agent 执行：Codex / Hermes → 处理视频/字幕/数据
   ↓
任务调度：飞书多维表格看板（下命令 + 看进度）
   ↓
知识管理：Obsidian（员工办公室 → 存 Skill 规则）
```

**核心理念**：
- 文案靠 CC（Claude Code）写，质量最高
- 其余重复任务靠 Agent 批量处理
- 飞书看板 = 完全没必要再做内容工厂网站
- 配置参数直接用飞书在线表格填写

## 🔑 可迁移到昆仑增长的关键洞察

### 洞察 1：「对话记忆」≠「项目能力」
沉淀到文件（AGENTS.md/Skill.md）才是真正可复用的能力

### 洞察 2：飞书多维表格是最低成本的 Agent 控制台
不需要开发任何界面，直接用飞书表格下命令、看进度

### 洞察 3：回归测试是生产级 Agent 的必要步骤
每次升级后必须测，新开对话后必须测

### 洞察 4：脚本负责确定性，Agent 负责语义，验证器负责底线
三者分工明确，不能混用
